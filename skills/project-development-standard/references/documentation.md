# 项目文档基础规范

用于项目文档编写、维护、整理和评审，不用于普通对话的落盘。项目已有目录、命名、模板或检查规则时沿用；没有约定时采用以下最小组织方式，不自动创建整套目录和模板。

## 分类与命名

- 写之前按功能名、接口、配置和同义词搜索已有资料，优先更新权威文件；临时分析和进度默认留在对话，用户要求保存或项目明确要求时再写文件。
- 同一事实只维护一个权威位置，其他文档引用它。区分使用指南、接口参考、设计方案和评审记录，避免每轮开发生成相同内容的副本。
- 没有项目约定时，功能文档优先放在现有文档区的对应功能目录；文件采用小写英文连字符，按用途使用功能名加 feature、api、design 或 review 后缀。README 等工具约定入口保留，不机械重命名存量文件。
- 不用“最终版”“优化版”或随意 V2 / V3 制造副本；真实多版本协议分别说明适用范围。日期只用于确有时点意义的计划、事故或历史证据。
- 每份新文档应能从已有项目或功能索引找到；索引只维护导航与用途，不再复制整份接口或运行契约。

## 内容与示例

- 默认使用中文，标题与术语统一；代码块声明语言，带字段注释的 JSON 使用 jsonc，并说明真实请求不传注释。
- 接口沿实际入口、业务逻辑、模型和消费端核查。说明字段类型、必填、默认值、单位、枚举、鉴权、错误和副作用，不臆造固定 Controller 分层、GET / POST 或统一响应结构。
- 配置写清位置、类型、默认值、单位、缺失及故障行为、缓存传播、是否重启和恢复方式，区分业务有效期与缓存续期。
- 明确区分已确认需求、当前实现、设计建议、实际验证及部署状态。代码与需求不一致时先记录差异，不能改文档把缺陷写成设计，也不能将计划写成已上线。
- 示例使用虚构值或占位符，不写真实凭据、个人路径或内部业务数据。项目内部文档也需按授权和读者范围处理敏感信息。

## 最小内容骨架

下列是无项目模板时的内容参考，只保留实际适用部分，不新建空章节或额外文档：

- 功能说明：目的与适用范围、主要行为、配置与使用、边界和故障处理、相关入口。
- 接口参考：路径与方法、鉴权、入参与字段说明、成功与典型失败响应、状态及限制；契约有变时标明新增、修改和兼容影响。
- 技术方案：目标与非目标、当前实现与问题、方案和取舍、影响与兼容、安全和异常、验证及上线回滚条件、待确认项。
- 当前评审：核查范围与版本、问题及证据、影响与建议、未解决项及结论限制；没有真实验证不能写“全部通过”。

## 更新与清理

- 直接修订同一份当前方案或评审，不默认保留每轮聊天版本；正式审批、风险接受、发布验收和未解决风险按项目要求保留证据。
- 移动、改标题或删除前扫描相对链接、锚点、索引、脚本及实际外部消费者；外部收藏是否需要重定向或兼容入口另行确认。
- 删除先说明具体文件、理由、有效内容承接、引用影响和恢复方式，并取得明确批准；“整理”不自动授权删除历史证据。
- 仓库内引用优先相对路径，不依赖个人目录。不能把缺失仓库或无法访问的文档视为已核实，不为了通过检查创建无内容占位文件。

## 验证边界

- 检查格式、文件与锚点引用、索引可达性、示例和语义一致性；新增未跟踪文件也要检查，不只看 Git 已跟踪差异。
- 使用项目已有检查命令并核实工作区、暂存区和 CI 基线含义。没有脚本时做范围匹配的核对，不擅自创建钩子或修改构建流程。
- 说明实际检查、遗留问题及无法核实的内容。链接或格式通过不能证明没有重复、代码一致、认证安全或已经部署。
