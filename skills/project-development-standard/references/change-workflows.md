# 任务执行流程

只执行当前任务相关步骤；公共标准按入口路由读取，具体目录、工具与业务契约从目标项目发现，不要求仓库采用统一技术栈。

## 需求与方案任务

- 适用于需求梳理、需求变更、技术方案、架构设计、接口设计、数据模型设计、实施计划及方案评审；先确定用户需要讨论、文档还是代码实现，不因触发本 Skill 自动扩大交付范围。
- 读取相关实现与已有方案，区分当前行为、已确认要求、设计建议及待确认问题；缺少代码或外部协议依据时明确标注，不把假设写成现状。
- 把需求落实为可观察的验收条件，说明正常流程、必要的失败边界及不在范围内的行为。只询问影响设计或实施的关键缺失信息；低风险假设可以明确说明后继续，不反复要求用户确认已经确定的事项。
- 按改动风险说明目标与非目标、调用链、影响模块、兼容性、异常与并发边界、验证及上线回滚方式；小改动只覆盖必要部分，不强制生成完整章节或全套文档。
- 比较实际可行的方案与取舍，复用项目已有能力。接口、数据及安全约束需要查到调用方与最终消费方；未实施的建议不能描述为已完成能力。
- 优先按项目已有模板更新同功能方案。仅在用户要求保存或项目规则明确要求时写入文档；仅要求方案评审时先给出问题、依据与待确认项，不自动实施或声称已获批准。

## 代码任务

### 理解实现与兼容性

- 根据现有代码、配置和测试，核对入口、业务编排、模型、外部依赖及最终消费方；涉及缓存时同时检查键、有效期、续期和故障行为。
- 优先使用可用的符号与引用工具；必要时使用文本搜索补查配置、脚本和非符号调用，不因工具缺失跳过调用方核查。
- 对仍有调用者的接口、数据结构或配置，先识别其兼容面。按项目要求选择独立实现、版本化、适配层或兼容扩展，不为追求统一直接改变旧行为。
- 修复前区分证据与假设，列清触发条件、修复后变化、失败分支和潜在受影响入口。
- 排查先限定环境、版本、时间和关联标识，用现有日志、测试或最小复现逐步验证假设；没有证据时不直接归因，也不为了排查擅自修改生产状态或输出敏感数据。

### 实施与验证

- 按[公共编码规范](coding-standard.md)与项目明确差异实施；涉及 Java 时再读取对应语言规范，不因为类名相似就套用另一项目的框架约定。
- 数据模型变更同时核对字段声明、构造/构建、读写、序列化及消费端。多端存在同名模型时分别核查，不按类名相同推断行为一致。
- 根据风险覆盖边界、异常、并发与存量行为，不为低风险文案修改强行启动整个系统，也不以轻量静态检查替代必要业务验证。
- 测试使用项目允许的入口、环境和时限；不可用时说明实际阻塞，禁止擅自改依赖、升级框架或关闭校验来制造通过。

## 文档任务

1. 按[文档规范](documentation.md)确定读者、用途、已有权威文件及项目模板，优先更新而不是新建副本。
2. 沿实际入口、模型、存储与调用方核对内容，标明当前实现、设计建议和未核实项，不以文档修订掩盖实现缺陷。
3. 修改后检查引用、索引、格式和语义，按授权处理清理；规范细节只在文档规范维护，本流程不重复定义。

## 联调验收与发布准备

- 联调前核对参与端的真实接口、字段、单位、状态与错误语义，以及目标环境、依赖和配置差异；契约未确认时先定位差异，不用猜测的请求或响应冒充已实现协议。
- 按需求验收条件关联实际验证证据，区分静态检查、单元测试、模拟依赖、真实联调和环境验收。缺少某一层证据时明确限制，不用其他层测试成功代替。
- 涉及发布时列清影响模块、配置或数据迁移、部署先后、新旧版本兼容、灰度与回滚条件；只覆盖本次实际需要的内容，不为所有项目强制引入灰度框架。
- 如已部署，按获授权的方式检查功能结果、关键错误和监控信号；没有环境访问或执行授权时交付核查步骤与待办，不声称上线成功，不自动执行部署、迁移或生产变更。
