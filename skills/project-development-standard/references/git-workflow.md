# Git 工作分支规范

用于命名、创建或选择本次任务的工作分支；普通开发任务仍可沿用已确认的当前分支。本规范不是新的 Git Flow，不改变项目的发布模型、默认分支、合并策略或权限。

## 先确认适用规则

- 先读项目 `AGENTS.md`、贡献指南和分支相关配置，核对用户指定名称、工具要求及 CI/发布的分支匹配条件。远端现有名称仅为线索，不能据此推断团队已经批准某套规则。
- 项目没有明确约定时使用下方默认格式；项目有可核实的格式时沿用，不自动修改流水线来适配本规范。
- 工具要求 `codex/` 等前缀时遵循该要求。若允许前缀后再分类，可用 `codex/feature/20261020-mfa-dchat-push`；若工具规定其他形状则按它执行，不能为了格式统一去掉强制前缀。
- 用户明确给出不符合默认格式的分支名时，说明差异并尊重已确认的选择；若违反 Git 语法或强制平台规则，先说明原因并确认替代名，不静默改写。

## 默认命名

```text
<type>/<YYYYMMDD>-<topic>
<type>/<YYYYMMDD>-<issue-id>-<topic>   # 只有提供了真实工单号时使用
```

`topic` 描述一个具体业务目标，使用小写英文字母、数字及单个连字符分词。不要使用中文、空格、下划线、大写混排、个人姓名、纯日期，或 `new`、`test1`、`final`、`v2` 这类无业务含义的修订后缀。真实协议版本可保留在主题内，例如 `feature/20261020-oauth2-token-exchange`。主题建议2至6个词，以能辨识任务为准，不机械凑词。

| type | 用途 | 示例 |
| --- | --- | --- |
| feature | 新功能及非缺陷类的一般维护，包括文档、工具、配置、测试、重构和优化 | `feature/20261020-mfa-dchat-push` |
| fix | 一般缺陷修复 | `fix/20261020-dchat-history-card` |
| hotfix | 已确认的紧急线上修复 | `hotfix/20261020-login-redirect-loop` |

- 默认只使用上述三种类型，不再单独设置文档、日常维护、重构、性能或测试前缀。纯文档维护可用 `feature/20261020-mfa-guide`；修复附带文档或测试仍用 `fix`，普通修复不能仅为了优先级使用 `hotfix`。
- 日期用分支创建当天，按项目约定的时区生成；项目未规定时使用当前工作环境日期并说明。后续开发、提交、合并或继续同一任务不改日期，不能每天生成一个新的同需求分支。
- 同一需求跨服务使用同名分支，并沿用该需求首次创建工作分支时确定的日期、类型和主题；后续接入的服务也不另换日期。类型或平台约定冲突时先说明，不能静默使用不同名称。
- 工单号可写为 `fix/20261020-iam-123-dchat-history-card`，只规范字母大小写，保留原编号并在任务中说明对应关系；没有工单号时不编造。若工单系统或项目要求原始大小写，沿用其明确规则。
- `master`、`main`、`feature_online`、`pre` 等项目已定义的长期分支不加日期，也不套用工作分支格式。正式 release、环境和长期集成分支由项目单独规定，不自动创建或重命名。
- 按名称排序时先按类型分组，同类型内按日期排列；日期表示创建时间，不代表最近提交时间。

## 创建与复用

1. 先检查当前分支、工作区及暂存区改动、现有 worktree、本地和已知远端分支。保留未提交内容，不自动暂存、丢弃、stash、切换或创建 worktree。
2. 确认创建授权和基线。优先使用用户或项目指定的起点；没有约定时先识别远端默认分支及发布模型，仍不明确再询问，不把 `master`、`main` 或当前分支硬编码为所有项目的起点。
3. 要求基于“最新”代码时，经允许的只读远端核查或 fetch 确认实际提交，再从该引用创建；无法联网时说明只核对了本地引用，不能声称已同步远端。不要为更新基线在脏工作区直接 pull、merge 或 rebase。
4. 按默认格式或项目例外检查名称，并使用 `git check-ref-format --branch "<候选分支名>"` 验证 Git 语法；再用 `scripts/check_branch_name.py <候选分支名>` 校验默认格式（type 白名单、日期、topic 字符与禁用词）。该命令不能证明符合团队规范；本地和远端的同名引用及目录前缀冲突仍需单独核查。
5. 同名分支已存在时核对是否属于同一任务和预期基线。明确续做且内容相符时复用；归属不明或不是同一任务时先确认，不覆盖、不重置，也不自动追加 `-2` 或日期规避冲突。
6. 同一需求涉及多个服务时，复用本需求已确定的完整工作分支名，各自核对基线和授权；缺失仓库不创建占位目录。创建分支不等于切换分支，也不等于提交、推送或合并。
7. 完成后报告实际分支名、基线引用及提交、创建或复用、是否已切换，以及未核实的远端范围；命名检查与 Git 操作结果分别说明。

## 存量与执行边界

- 只约束新任务新建的工作分支，现有分支不追溯改名或补日期；跨服务续做现有任务优先沿用已确认的完整旧名称。重命名或删除已发布分支前，说明 PR、CI、部署和其他使用者的影响，并取得明确批准；不自动强推或删除远端分支。
- 仅讨论命名规范、审查代码或修改文档，不构成创建实际业务分支、提交、推送或合并的授权；继续遵守项目原有确认要求。
- 安装 Skill 不会新增提交钩子、服务端分支策略或 CI 门禁。需要自动检查时在项目中另行接入；文档检查钩子不等于已验证分支命名。
